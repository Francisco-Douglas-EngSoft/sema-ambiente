# Prompt Reutilizável — Limpeza de Referências Lovable + README Profissional

> Copie e cole este prompt no Kiro ao abrir qualquer novo projeto para executar
> a limpeza de referências externas e gerar um README completo e profissional.

---

## O Prompt

```
Faça uma análise completa deste projeto e execute as seguintes tarefas na ordem abaixo:

---

### TAREFA 1 — Análise do Projeto

Antes de qualquer alteração, leia e mapeie:
- O objetivo e propósito do sistema (o que faz, para quem serve)
- A stack tecnológica completa (frameworks, bibliotecas, ferramentas, banco de dados)
- A arquitetura e estrutura de pastas/módulos
- Todas as funcionalidades implementadas
- Os scripts disponíveis no package.json (ou equivalente)
- As configurações de backend/banco de dados

---

### TAREFA 2 — Remover todas as referências ao Lovable / lovable.dev

Faça uma busca global por "lovable", "Lovable", "lovable.dev", "gpt-engineer", "GPT Engineer"
em TODOS os arquivos do projeto (incluindo package.json, vite.config.ts, index.html, src/**,
README.md, etc.) e execute as correções abaixo:

1. **vite.config.ts** — Remover o import e uso de `componentTagger()` da `lovable-tagger`.
   Simplificar para uma `defineConfig` estática sem o modo condicional de desenvolvimento.

2. **package.json** — Remover `lovable-tagger` das devDependencies.
   Se o `name` do projeto for genérico (ex: `vite_react_shadcn_ts`), renomear para o nome
   real do projeto em kebab-case.

3. **src/integrations/supabase/client.ts** (se existir) — Remover o comentário
   `// This file is automatically generated. Do not edit it directly.`

4. **src/App.tsx** (ou arquivo raiz de rotas) — Substituir comentários instrucionais do
   template Lovable (ex: `{/* ADD ALL CUSTOM ROUTES ABOVE THE CATCH-ALL "*" ROUTE */}`)
   por comentários neutros e em português.

5. **README.md** — Apagar todo o conteúdo gerado pelo template Lovable.
   Será substituído na Tarefa 3.

6. **Desinstalar o pacote**: Execute `npm uninstall lovable-tagger --save-dev`
   para remover o pacote do node_modules e atualizar o package-lock.json.

7. **Verificação final**: Após todas as edições, confirme que nenhum arquivo de
   código-fonte (exceto lockfiles como bun.lock e package-lock.json, que são gerados
   automaticamente) ainda contém referências ao Lovable.

---

### TAREFA 3 — Criar o README.md completo, moderno e profissional

Com base na análise feita na Tarefa 1, crie um README.md do zero seguindo esta estrutura:

1. **Cabeçalho centralizado** com:
   - Emoji temático + nome do projeto em H1
   - Subtítulo descrevendo o sistema em uma linha
   - Badges das principais tecnologias (shields.io, style=flat-square)
   - Badge de licença MIT

2. **Visão Geral** — 2 a 3 parágrafos explicando o que o sistema faz e para quem

3. **Funcionalidades** — Listagem por módulo com ícones emoji, bullets claros e objetivos.
   Incluir fluxos de status quando relevante (ex: `pendente → resolvido`).

4. **Stack Tecnológica** — Tabela com as camadas: Framework UI, Bundler, Estilização,
   Roteamento, Estado assíncrono, Formulários, Gráficos, Backend/BaaS, Testes, etc.

5. **Estrutura do Projeto** — Árvore de diretórios comentada mostrando as pastas principais

6. **Banco de Dados** (se aplicável) — Tabela com as entidades principais e suas descrições.
   Listar funções RPC/stored procedures se existirem.

7. **Início Rápido** — Pré-requisitos, instalação (git clone + npm install),
   variáveis de ambiente (.env de exemplo) e comando para rodar em dev.

8. **Scripts Disponíveis** — Tabela com todos os scripts do package.json e suas descrições

9. **Deploy** — Opções de hospedagem estática (Vercel, Netlify, Cloudflare Pages)

10. **Contribuindo** — Fluxo padrão: fork → branch → commit (Conventional Commits) → PR

11. **Licença** — MIT

12. **Seção do Desenvolvedor** — Incluir exatamente o bloco fixo abaixo ↓

---
```

## Notas de Uso

- Funciona para projetos **React/Vite**, mas a lógica da Tarefa 2 se adapta a qualquer stack —
  ajuste os arquivos mencionados conforme necessário (ex: `next.config.ts` em vez de `vite.config.ts`)
- Se o projeto usar **Yarn** ou **Bun**, substitua `npm uninstall` pelo equivalente:
  `yarn remove lovable-tagger` / `bun remove lovable-tagger`
- O `bun.lock` gerado dentro do sandbox da Lovable pode conter URLs internas do registry GCP —
  isso é inofensivo para o runtime, mas pode ser deletado se o projeto migrou para npm
- A **seção do desenvolvedor** é fixa e deve ser sempre a última seção do README, sem modificações
